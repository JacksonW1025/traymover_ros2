# AGX Orin 底盘反馈实测与里程计字段核对

实测日期：2026-11-17，约北京时间 14:11–14:16。对象是本工作区连接的底盘，
不是仅依据图片转录推导。原始数据、发送帧和离线解析结果见
[`serial_capture_20261117/`](serial_capture_20261117/)。本次未修改现有底盘驱动或 YAML 默认参数。

## 1. 结论与证据边界

**能获取与里程计有关的真实运动反馈。** 在发送速度始终为零的情况下，用户手动小幅
原地晃动车轮，`0x02/0x60` 成功回包中的 `11–14` 和 `29–32` 字节随之出现正负变化。
因此这不是简单回显上位机速度指令；手动转轮已经足以验证反馈链路，不需要主动驱动电机。
但这不等于已经验证断电电机状态下的反馈：本次底盘控制器保持上电。

**所有索引从帧首字节起按 0 开始计数，是字节偏移，不是 bit 编号。**

| 成功电机数据帧中的位置 | 从 1 数的位置 | 解码 | 本次判断 |
|---|---|---|---|
| `11–12` | 第 12–13 字节 | 大端有符号 int16 | 左侧编码器/运动增量候选；确实随转轮变化，绝对单位待标定 |
| `13–14` | 第 14–15 字节 | 大端有符号 int16 | 右侧编码器/运动增量候选；确实随转轮变化，绝对单位待标定 |
| **`29–30`** | **第 30–31 字节** | **大端有符号 int16 / 1000** | **车体线速度候选，按原协议为 m/s** |
| **`31–32`** | **第 32–33 字节** | **大端有符号 int16 / 1000** | **车体偏航角速度候选，按原协议为 rad/s** |

位置和运动相关性已实测；速度的 `/1000` 单位沿用协议，**尚未通过已知距离/转角验证绝对比例**。
左右轮的物理对应、正方向也尚未通过逐轮、定向实验独立确认，表内左右名称沿用旧驱动。
这批帧没有已确认的绝对 `x/y/yaw`；位姿需要上位机积分。
尚不能宣称完整协议已逆向完成或轮式里程计已完成精度标定。

## 2. 迁移后实际连接问题

实机内核 `5.15.148-tegra`，L4T **R36.4.4**。USB 枚举与接收结果如下：

| USB 芯片 | 实际串口 | 身份证据 |
|---|---|---|
| `1a86:55d4`，序列号 `5A6C071391`，cdc_acm | `/dev/ttyACM0` | 115200 下约 100 Hz、反复以 `5A A5 4C 00` 开头，符合所接 IMU 的数据流特征；未发现有效底盘帧 |
| `1a86:7523`，CH340，USB 路径 `1-4.4` | 恢复驱动后 `/dev/ttyUSB0` | 查询得到校验有效的 `7F 7F 28 03 60` 及 `7F 7F 28 02 60` 回复，确认连接 STM32 协议端点 |

发现的障碍：

1. 仓库底盘配置仍为 `/dev/ttyCH341USB0`，本机没有这个节点；IMU 默认的
   `/dev/ttyCH343USB0` 也与实测不同。
2. CH340 能被 `lsusb` 看见，但初始没有绑定串口驱动。当前内核模块目录里没有 `ch341.ko`。
3. 加载驱动后，`brltty` 抢占接口，使 `/dev/ttyUSB0` 再次消失。内核明确记录
   `interface 0 claimed by ch341 while 'brltty' sets config #1`。
4. 当前用户不在 `dialout` 组，常规设备权限是 `root:dialout 0660`，本轮以 sudo 采集。
5. 系统 Python 缺少 `serial`（pyserial），现有驱动测试不能正常收集；因此本次采集使用标准库。

本次做了以下**临时系统操作**以完成实测，未持久安装驱动：

- 下载 [Linux v5.15 官方 ch341.c](https://github.com/torvalds/linux/blob/v5.15/drivers/usb/serial/ch341.c)，
  在 `/tmp/traymover_ch341/` 用本机内核头文件编译；`Makefile` 内容为 `obj-m += ch341.o`。
- 执行 `modprobe usbserial`、`insmod /tmp/traymover_ch341/ch341.ko`。
  构建成功且加载成功；内核记录未签名模块导致 taint，未开启强制加载或跳过版本检查。
- 初次终止抢占进程后它被 udev 重新激活，故最终执行
  `systemctl mask --runtime --now brltty-udev.service`，再将 `1-4.4:1.0` 绑定回 ch341。
- 结束时关闭了所有采集口与提权 shell。临时驱动仍加载，runtime mask 仍保留；重启后均不保证保留。
  恢复该服务的运行许可可执行 `sudo systemctl unmask --runtime brltty-udev.service`，但可能再次抢占串口。

源码 SHA256：`0568953df7e73445ca16e21e685a8c06a3c33891e6976be34e28f6eee7cd1912`。
临时模块 SHA256：`d0df17c6a1b87e65e1e70412436a6172967173eba332b15e314261e02a4a9c35`。
后续正式部署应解决匹配内核的驱动安装、精确的 brltty 设备排除和串口用户权限。
目前底盘 by-id 为 `/dev/serial/by-id/usb-1a86_USB_Serial-if00-port0`，不含独立序列号，
增加同型转接器时不能依赖它区分设备。IMU 的 by-id 为
`/dev/serial/by-id/usb-1a86_USB_Single_Serial_5A6C071391-if00`。

## 3. 采集方法与统计

串口参数：115200、8N1、无软硬件流控。单进程独占读取，接收块记录相对单调时钟时间；
不按一次 `read()` 分帧，也不按 `0D 0A` 搜索切帧，因为负载可能含有相同字节。
时间戳是读取块时刻，不是 MCU 测量时间戳。

| 文件 | 操作 | 校验有效的接收帧 |
|---|---|---|
| `acm0_passive_115200.jsonl` | 8 秒静听 IMU，无 TX，65595 字节 | 底盘帧 0 个 |
| `usb0_passive_115200.jsonl` | 12 秒静听底盘，无 TX，1257 字节 | `00/80` 1 个，`04/80` 30 个；没有成功电机数据 |
| `usb0_status_query.jsonl` | 8 秒，约 2 Hz 查询 ID 3，复位/清零字段均 0 | `03/60` 16 个，`00/80` 1 个 |
| `usb0_data_query.jsonl` | 60 秒，约 20 Hz 零速度 ID 2；后段用户手动晃动 | **`02/60` 1199 个**，`03/80` 1 个 |
| `usb0_data_settle.jsonl` | 再采 20 秒零速度 ID 2，包含结束阶段/微动 | `02/60` 399 个，`5E/80` 1 个 |

表中 `ID/Status` 均为十六进制。各底盘文件有少量起始杂字节，不强行解释为协议内容；
解析器对齐到完整帧头后，没有发现头部匹配但校验失败的候选帧。
这不等于链路从未丢字节。错误帧 ID 有多种取值，不能仅凭 `04/80` 认定“消息数量为 4”。
无 TX 时出现错误帧，可能与固件超时行为有关，本次没有验证其触发机制。

ID 3 查询帧：

```text
7F 7F 28 03 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00
00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 D7 0D 0A
```

本次 ID 2 帧如下，线速度与角速度字段都是 0。**它同时写入参数，不是纯只读查询**：
沿用现有配置轮径 170 mm、轮距 455 mm、gear=5600、tick ratio=10、左右 scale=1、
IR 阈值=20、LED=1；未发送电机复位、告警清除、顶升或非零速度。
本次没有先读取到固件原有机械参数，不能保证这些参数与原值一致。

```text
7F 7F 28 02 00 00 00 00 00 00 00 00 00 00 00 01 00 01 00 00
00 01 00 14 14 14 AA 15 E0 01 C7 0A 00 00 00 00 00 28 0D 0A
```

## 4. 已验证的分帧与解码

40 字节定长；头 `7F 7F`，长度字节 `28`，尾 `0D 0A`；
`checksum = (-sum(frame[0:37])) & 0xFF` 位于 byte 37，等价于 `sum(frame[0:38]) & 0xFF == 0`。
只将 byte 3 为 `02`、byte 4 为 `60` 的完整校验帧送入电机数据解码。
`80` 错误帧不能被当作零速反馈，否则会产生假的停车判定。

以下是捕获到的运动帧（相对该段采集开始约 56.229 秒）：

```text
7F 7F 28 02 60 00 01 47 00 00 00 EF 50 01 31 00 32 00 05 00
32 00 32 00 E1 00 B3 00 00 FF E6 FF B2 02 00 01 BA 3D 0D 0A
```

- `[11:13] = EF50` → `-4272`；`[13:15] = 0131` → `305`。
- `[29:31] = FFE6` → `-26` → 文档比例下 `-0.026 m/s`。
- `[31:33] = FFB2` → `-78` → 文档比例下 `-0.078 rad/s`。
- byte 37 为 `3D`，头尾、长度与补码校验均通过。

解码示例（输入必须已通过上述检查）：

```python
left_raw = int.from_bytes(frame[11:13], 'big', signed=True)
right_raw = int.from_bytes(frame[13:15], 'big', signed=True)
vx = int.from_bytes(frame[29:31], 'big', signed=True) / 1000.0
wz = int.from_bytes(frame[31:33], 'big', signed=True) / 1000.0
```

主采集中的原始范围：左 `-9918…11596`，右 `-5951…6561`，vx `-26…26`，wz `-254…156`。
前约 34 秒除首个右轮残留 `-152` 外，编码器和速度为零；约 34.6 秒起随用户手动运动变化。
速度存在量化：vx 常见 `0/±8/±17/±26`，wz 常见 `0/±19/±39/±58/±78`。
微小运动可能只在编码器字段出现，速度字段仍为零，不应要求每一帧二者完全对应。
结束段仍有零星 `±152` 编码器值与 `-19/-39` 角速度，不能据此建立静止噪声阈值。

## 5. 编码器字段不能直接按当前 YAML 换算

原 ROS1 实现累加每帧 `11–14` 的 int16，支持它们是增量而非绝对累计计数的解释。
本次运动后字段频繁回到零，也符合增量特征；没有独立验证“每查询清零”还是固定 MCU 周期累积。
首帧/重新打开后可能带有历史积累，应丢弃首次增量以建立基线。

非零值常见 `152、305、457、610、762、915…`，呈约 `152.6` 的量化阶梯，
**不像可直接认定的一 tick 一个原始编码器脉冲**。它可能已经经过固件换算；本次不确定单位。
不要直接套用 `π × wheel_diameter / (gear_reduction × tick_meter_ratio)`，
也不要在未证明累计计数语义前对相邻值再次差分。当前 `right_encoder_sign=-1` 同样没有被本轮定向验证。

要获得可靠轮距/距离尺度，需要逐轮已知圈数、整车已知直线距离与已知转角实验，并改变查询频率
检验增量积累周期。速度与增量也可能存在采样/滤波延迟，本次不能给出确定延迟参数。

## 6. 其余字段及原文档修订点

| 偏移（0x02 成功帧） | 本次值 | 名称/解释及可信度 |
|---|---|---|
| 0–4 | `7F 7F 28 02 60` | 帧头、长度、消息 ID、成功状态，已验证 |
| 5 / 6 | `0 / 1` | 按文档急停/初始化；未实际切换急停验证 |
| 7 / 8 | `71 / 0` | 按文档电量/充电；电量 71%，未用外部仪表验证 |
| 9 / 10 | `0 / 0` | 左右告警，未触发验证 |
| 11–14 | 随运动变化 | 编码器/增量候选，见前文 |
| 15–16、19–20、21–22 | 均为 50 | 按文档 TOF，单位、左右次序和是否真实有效均未验证 |
| 17 | 0 | 按文档外部反馈引脚，未验证 |
| **18** | **5** | **与文档仅列 0/1/2 冲突，不能直接发布为“上升/下降”** |
| 23–24 / 25–26 | 215–230 / 177–181 | 按文档防跌落候选，含义、单位、有效性未验证 |
| 27 / 28 | `0 / 0` | 按文档电机锁/关机，不能据此独立判定电机使能状态 |
| 29–32 | 随运动变化 | vx/wz，见前文 |
| 33 / 34 | `2 / 0` | 模式/综合 bitfield；模式含义及 bit 映射未切换验证 |
| 35–36 | `01 BA`（442） | 版本候选；不推测十进制版本号编码 |
| 37–39 | 校验 + `0D 0A` | 已验证 |

ID 3 的成功样本为：

```text
7F 7F 28 03 60 00 1B 00 00 02 00 00 00 00 00 00 00 00 00 0D
00 00 00 00 00 01 BA 00 00 00 00 00 00 00 00 00 00 92 0D 0A
```

其 byte 5–6 为 27、7–8 为 0、9 为 2、19 为 `0D`、25–26 为 `01BA`，
20–24 为零。这些是原始值，温度/电流单位和开关 bit 布局未验证。
`stm32_to_ros2_protocol.md` 将其 **10–13** 标为 Speedx/Speedth；
但 `reference/example_ws/src/robot_driver/src/driver_ros.cpp` 的 `check_status()`
明确按 **Left_PWM / Right_PWM** 解析，当前 Python `parse_motor_status_frame()` 也采用这个命名。
因此应将该段标为“左右控制/PWM 候选，有争议”，不能复用 ID 2 的速度解码。
本次 ID 3 查询阶段没有定向运动实验，无法仅靠这些零值最终裁决语义。

同理，byte 34 的 bit0–7 文档目前仍只是待验证定义，不能宣称完整协议已经确认。
原 ROS→Driver 文档中的静态查询数组 byte 37 为零，多数不能直接发送；必须重新计算校验。
它所列 get_baud 的 ID 0 也与 ID 1 定义矛盾，本次未发送，不将其视为可靠模板。

## 7. 对接 /odom 的建议与现有实现风险

当前 `traymover_robot.py` 已解码上述位置，并在 `handle_motor_feedback()` 中用反馈 `vx/wz`
按中点朝向积分；并非只有电量解析。YAML/启动日志仍描述“编码器增量里程计”，与实际积分路径不一致。
本轮不修改运行行为，避免把未经标定的推断直接写入导航链路。

后续可以优先使用 ID 2 的速度候选作为 `Odometry.twist`，完成比例和方向标定后积分位姿：

```text
yaw_mid = yaw + wz * dt / 2
x += vx * cos(yaw_mid) * dt
y += vx * sin(yaw_mid) * dt
yaw += wz * dt
```

需要处理首次帧、丢帧、重连和长时间间隔：不应把断连后当前一帧速度乘上整段断连时间。
本协议中没有已确认的 MCU 测量时间或序列号，上位机接收间隔会包含 USB 调度抖动。
在比例、时序和正方向验证前，不应把这一结论直接视为导航精度保证。
