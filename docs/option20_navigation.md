# 选项 20：二维定位、保守导航与三维展示

选项 20 使用 **FAST-LIO 激光惯性里程计 → AMCL 二维定位 → Nav2**。NDT 不参与定位，也不为三维地图显示而启动。底盘不提供运动反馈；`/odom` 来自激光与 IMU 测量得到的连续位姿及其速度估计，不能用下发速度冒充里程计。

## 三个高度带如何帮助定位

当前方案使用相对地面 **1.10～1.50 m、1.50～1.90 m、1.90～2.30 m** 三个高度带的点云并集。在每个水平角度格中取距离最近的真实回波，生成一个 `/scan_localization`，交给一个 AMCL。没有回波的角度保持无穷远，不凭空补点。

这三个带不是雷达固定的三条 ring，也不是三个各自输出位姿的 AMCL。固定 ring 对应的是发射角：同一条 ring 在不同距离处照到的高度不同。高度带有助于收集更多墙面、立柱等结构；逐带统计可以判断现场哪一带缺乏观测。多个带仍共享同一雷达、相似遮挡和同一地图，不能当成三个独立定位证据。

默认扫描覆盖 360°，角度格宽 0.5°，距离范围 0.5～50 m。实时状态中的 `band_bins` 是各带覆盖的有效角度格数，`bins` 是并集有效格数，重叠格不会重复计入并集：

```bash
ros2 topic echo /option20/scan_status
```

三个高度带目前连续相接，因此几何上等价于 1.10～2.30 m 的联合高度窗口，但保留分带统计，便于后续依据现场观测选择真正有用的带。高处人体、广告牌和移动物体仍可能进入定位扫描；AMCL 的 beam skipping 只能缓解部分地图不一致。

## 构建与启动

从工作区根目录执行：

```bash
source /opt/ros/humble/setup.bash
colcon build --symlink-install --packages-select \
  fast_lio turn_on_traymover_robot traymover_robot_safety traymover_robot_nav
source install/setup.bash
bash scripts/traymover.sh
```

1. 如有此前启动的机器人栈，先用菜单 **0** 停止，避免重复占用传感器、底盘和 TF。
2. 选择菜单 **20**，地图选择 **1**，核对显示的文件名。
3. 等待地图预处理及进程启动。当前大 PCD 的转换和三维显示加载需要时间；每次运行生成独立日志目录，不改写源地图。
4. 在 RViz 三维画面中找到实际所在区域，用 **2D Pose Estimate** 给定当前位置和朝向。不要直接发送导航目标。
5. 查看 RViz 的 **Option 20 Health** 面板，等待绿色 `Ready for goal: TRUE`，并确认机器人、扫描与墙柱的位置关系合理。
6. 先给同一可见通道内的短距离 **2D Goal Pose**，观察停车、朝向调整、实时障碍和里程计连续性，再逐步扩大路线。
7. 测试结束使用启动终端 **Ctrl+C**，或回主菜单选择 **0** 收尾。菜单退出本身不应当作完整停车步骤。

健康输出命令：

```bash
source /opt/ros/humble/setup.bash
source install/setup.bash
ros2 topic echo /option20/health --no-daemon
```

RViz 已默认加载 **Option 20 Health** 面板，直接订阅上述话题。绿色表示 `ready_for_goal` 为真；未就绪时显示原因。没有消息、数据非法或超过 1 秒未收到新鲜状态时显示未知/超时，不会继续保留绿色。面板是只读显示，不发送速度或解除急停。

“可以给目标”与“当前速度指令获准执行”分开显示：空闲时 `ready_for_goal` 可以为真，而 `ready` 为假、输出速度为零，这是正常等待目标。已有 RViz 窗口需重启以加载新插件；自定义布局也可在 **Panels → Add New Panel → traymover_robot_safety/Option20HealthPanel** 手动添加。

二维定位图、二维通行图和三维点云共用整平后的 `map` 坐标。RViz 中的机器人和路径因此位于同一个三维场景，导航计算仍在地面平面内进行。这个坐标一致性不意味着路径、避障行为会与旧三维导航算法逐帧相同，也不提供跨楼层或坡道的三维规划能力。

`ready_for_goal` 表示传感器、定位、急停等条件连续稳定，已经可以给目标。没有目标时可能同时看到 `ready: false` 和 `command:stale`，这是没有新鲜导航速度指令导致的正常零输出，不应因此绕过门控。运行中有任何拒绝原因都会使门控输出零速；健康恢复后还需要恢复时刻之后的新指令。

## 日志与现场排查

每次运行会打印 `logs/nav/<UTC时间>_option20.<随机后缀>/`，内含：

- `map_preparation.log`：地面拟合、变换、地图统计及预处理错误。
- `maps/`：本次配对地图和 manifest。
- `launch.log`、`ros/`：启动与节点日志。
- `health.log`：最终门控健康状态。
- `fastlio/`、`diagnostics.log`：里程计诊断。
- `nav2_params.yaml`、`software_commit.txt`：本次参数副本和提交标识；提交标识不包含尚未提交的改动。

可进一步查看：

```bash
ros2 topic echo /option20/odom_status --no-daemon
ros2 topic echo /option20/depth_status --no-daemon
ros2 topic echo /option20/lidar_status --no-daemon
ros2 topic echo /traymover_estop/auto_reason --no-daemon
ros2 topic info /option20/cmd_vel_safe --verbose
```

以下阈值来自 `option20_guard.py` 和传感器适配节点当前默认值：

| 健康原因或现象 | 判定与处置方向 |
| --- | --- |
| `localization:not_initialized` / `initializing` | 尚未收到初始化后的有效 AMCL；在 RViz 给定正确位置和朝向，等待稳定。 |
| `localization:stabilizing` | 至少需要 3 次合格定位更新，再连续健康 0.8 s；节点定期请求 AMCL 静止更新，不需要靠开车强行触发。 |
| `localization:uncertain_pose` | x/y 标准差上限 0.40 m、yaw 标准差上限 0.25 rad；检查初值、重复结构、遮挡及地图适用性。 |
| `localization:global_correction_jump` | 相邻全局校正平移超过 0.35 m 或转角超过 0.25 rad；门控停车，检查匹配，不把跳变当真实车体运动。 |
| `scan:insufficient_map_agreement` | 至少 30 个有限回波，并有至少 25% 在地图占用端点 0.30 m 邻域内；检查位置、朝向、高度带、结构覆盖和动态遮挡。 |
| `odom:*stale*` | 门控里程计及其状态时效为 0.40 s；检查 FAST-LIO 延迟、IMU/雷达时间戳和计算负载。 |
| `scan/lidar/depth:*stale*` | 门控传感器及状态时效为 0.60 s；传感器适配层自身接受的输入年龄上限为 0.50 s。 |
| `amcl:*stale*` | 定位消息时效为 2.50 s；检查初始位姿、扫描、TF 和 AMCL 生命周期。 |
| `depth:insufficient_valid_pixels` | 门控要求至少 10% 有效采样深度；适配层自身最低门槛为 5% 且不少于 30 点，最终以更严格门控为准。检查镜头、范围、CameraInfo 和 TF。 |
| `estop:*` | 手动/综合急停必须明确解除；自动急停请求须持续到达且为 false，超时 0.30 s 即停车。先处理真实原因，沿用现有急停操作，不发布伪造状态解除。 |
| `command:multiple_safe_publishers` | 最终速度话题出现额外发布者；停止额外控制进程，不并行启动键盘/其他导航栈。 |
| `command:invalid_or_reverse` | 指令非法、包含不支持的分量或要求倒车；当前策略禁止倒车。 |
| `obstacle:stop_envelope` | 雷达或深度点进入停车包络；等待障碍消失，或检查是否存在车体反射/外参问题，不删掉真实障碍来开车。 |
| 规划失败或目标不可达 | 检查目标是否落在未知区、障碍、膨胀区或不连通区域；不要将未知区整体改成自由区。 |
| `odometry_gap` / `odometry_jump` / `odometry_timestamp_reset` | 里程计间隔超过 0.75 s、瞬时速度超过 1.5 m/s 或角速度超过 2.5 rad/s、时间戳倒退会锁存故障。排查后用菜单 0 完整结束，再重启 20 并重新定位；不热重置 TF 原点继续走。 |

时间戳超过当前时间 0.10 s、重复或倒退也会拒绝。若现场持续达不到时效门槛，应定位数据积压、传感器时间和负载问题，不能只增大超时来获得绿色状态。

## 速度、急停与边界

最终速度链路为：

```text
Nav2 → /option20/cmd_vel_nav → option20_guard
     → /option20/cmd_vel_safe → 底盘自身急停与速度看门狗
```

需要立即停车时，使用现有物理/手动急停，或 RViz 的 **Traymover EStop → EStop**；测试结束仍按前述 Ctrl+C/菜单 0 收尾。面板 **Free** 只请求解除手动急停，不能覆盖仍然有效的自动急停或门控拒绝原因。

底盘订阅被限制到专用安全输出。不要向 `/option20/cmd_vel_safe` 手工发速度，也不要把键盘遥控重映射到这个话题；它不是手动驾驶入口。选项 20 不需要并行启动其他 teleop。已有手动和自动急停保持有效，门控不负责替人或替传感器解除急停。

默认最大线速度 0.14 m/s、最大角速度 0.35 rad/s，线加速度上限 0.12 m/s²、角加速度上限 0.40 rad/s²。停车包络在车体尺寸外至少留 0.15 m，并按实际估计速度、0.60 s 反应时间和 0.20 m/s² 减速度估算距离；转弯还计入扫掠范围。这些是初始保守软件参数，真实停车距离必须现场测量。

Nav2 启用碰撞检查、动态障碍和膨胀层。默认不倒车，不运行盲目旋转/倒车/清图恢复；正常控制器仍可在目标或路径方向需要时调整朝向，并受到同一停车包络约束。阻塞期间以等待和重新规划为主，不承诺一定能从人群中绕行脱困。

障碍点云只负责标记；两路独立的 `lidar_clearing` / `depth_clearing` 用真实近地回波清除旧动态占用，使用真实传感器原点。没有回波、NaN、无穷远和天花板点不会被转换成自由射线。

本机旧版 Nav2 的 bond 状态机曾在重复启动测试中抛出 `transition invoked while in transition`，导致节点已激活但管理器中止启动。选项 20 的两个生命周期管理器因此设置 `bond_timeout: 0.0`，关闭该层的自动故障联动；数据/速度看门狗、独立自动急停与底盘看门狗继续执行停车。节点故障后应整体重启选项 20，不依赖生命周期管理器自动恢复。这一设置仅限选项 20。

适用范围是一个近似平面的单层区域。以下限制仍在：

- 高位多线雷达和深度相机都有近地、侧后方盲区；玻璃、黑色/反光物体、台阶和落差不能由这套软件完整保证检测。
- 当前忽略 0.12 m 以下的障碍点，不适合未经检查的矮障碍或跌落边缘环境。
- 整平可以消除整体倾斜，不能修复非刚性地图重影、严重漂移、多楼层或明显坡道。
- 无底盘反馈时，局部运动仍依赖激光与 IMU。IMU 单独积分不能提供长期不漂移的位置；激光退化且 AMCL 也缺乏结构证据时，应停车，不能承诺永久无漂移。
- 重复立柱、长走廊和大面积人群遮挡仍可能让二维定位出错；协方差小和局部匹配分数高均不是绝对定位正确的证明。
